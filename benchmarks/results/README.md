# Benchmark results

**This directory is intentionally empty in version control.**

Results are generated by `./scripts/benchmark.sh` and are gitignored. Committing
them would mean shipping numbers from someone else's machine — a different GPU,
a different core count, a different thermal envelope — which is worse than
shipping no numbers at all, because they look authoritative.

```bash
./scripts/benchmark.sh
```

Writes timestamped JSON here:

| File | Produced by | Needs |
| --- | --- | --- |
| `cpp-queue-*.json` | `bench_queue` | C++ compiler |
| `cpp-scheduler-*.json` | `bench_scheduler` | C++ compiler |
| `cpp-memory-*.json` | `bench_memory` | C++ compiler |
| `cpp-histogram-*.json` | `bench_histogram` | C++ compiler |
| `cpp-kv_cache-*.json` | `bench_kv_cache` | C++ compiler |
| `operators-*.json` | `benchmark_kernels.py` | Python |
| `batching-*.json` | `benchmark_batching.py` | Python |
| `http-*.json` | `benchmark_server.py` | a running server |
| `cuda-kernels-*.json` | `bench_kernels` | **NVIDIA GPU** |

A Markdown summary is written alongside them:

```bash
python benchmarks/summarize_results.py benchmarks/results/
```

## Before reading any of it

Check `backend.using_custom_kernels`. On a machine without CUDA,
`operators-*.json` compares PyTorch against PyTorch and carries an explicit
`caveat` field saying so. A silent fallback to the reference path looks exactly
like a very slow custom kernel.

For CUDA results, compare `effective_bandwidth_gb_s` against the
`theoretical_bandwidth_gb_s` the harness reads from device properties. A raw
millisecond figure means nothing without that reference; a kernel at 80% of peak
bandwidth is essentially finished regardless of how it compares to another
implementation.

Method, and what each suite is actually measuring, is in
[../../docs/benchmarking.md](../../docs/benchmarking.md).
